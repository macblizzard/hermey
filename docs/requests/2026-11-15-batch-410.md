## Conventions

- Every item states: what exists today, what is requested, the decisions already taken, and the
  acceptance checks that prove it. An item is done when its acceptance checks are demonstrated, not
  when the code compiles.
- Standing product rules still hold: bot-first home screen, one endless conversation per bot, no
  session list, no tab bar. No item below may reintroduce any of those.
- Both apps ship together. A row that exists on the phone and not in the Mac sidebar is an
  incomplete item.

## R1 — Keyboard shortcut opens the bot menu (⌘E)

**Platforms:** [macOS] — [iOS] is iPad-with-keyboard, see decision.

**Today:** the bot's own page (`ConversationDrawer` on iOS) is reachable only by tapping the
conversation-header pill. The Mac has `CommandMenu`s in `HermesMacApp.swift` with ⌘⇧P, ⌘+, ⌘-, ⌘0,
⌘↩, ⌘., ⌘S, ⌘K, ⌘F bound. Nothing opens the bot page.

**Requested:** ⌘E opens the same bot page the pill opens, for the bot whose conversation has focus,
as a menu command inside the existing "Conversation" menu (so it is discoverable and listed with its
shortcut). Escape / ⌘E again closes it. Works whether the sidebar is visible or collapsed.

**Decisions taken:** the Mac gets the iOS drawer's content, not a second design; the command is
disabled (greyed) when no conversation is open.

**Acceptance:**
1. With a conversation focused, ⌘E opens the bot page; ⌘E again closes it.
2. The command appears in the Conversation menu with "⌘E" rendered next to it.
3. With no conversation open the command is disabled, not a no-op that silently opens nothing.
4. ⌘E does not collide with any existing binding (verified against the list above).

## R2 — Lower / compact the bot page header (face + name)

**Platforms:** [iOS] [macOS]

**Today:** `ConversationDrawer` opens with a generous header — portrait, name, subtitle, then the
verb groups. On a phone the verb groups are pushed below the fold, so opening the menu shows
portrait and nothing actionable.

**Requested:** make the header shorter and bring it down — smaller portrait, name and subtitle on
one to two tight lines, less vertical padding above it — so the first verb group is visible without
scrolling on a 6.1" phone, and two groups on a Pro Max.

**Decisions taken:** the portrait stays (it is the answer to "which bot am I editing"), but at a
compact size; the name keeps its full type treatment, the subtitle loses a line of leading; nothing
is removed from the verb list.

**Acceptance:**
1. On iPhone 16 Pro, opening the bot page shows the face, the name, the subtitle and the first verb
   group with no scrolling. Screenshot as evidence.
2. On the Mac bot panel, the same compact header, and the panel's total height shrinks by the same
   amount.
3. Nothing clips at the largest Dynamic Type setting.

## R3 — Search finds message content, not just bot names

**Platforms:** [iOS] [macOS] [bridge] [shared]

**Today:** the bot-list search filters rows by `displayName` and profile id
(`BotListScreen.filtered`, `SidebarBotList.matches`). Message text is not searchable from the list.

**Requested:** a search over **every bot's conversation content**, in addition to the existing name
match. Results are a list of *findings*, not rows of bots: each finding shows which bot, the
snippet with the query highlighted, the message's time, and the role (you vs the bot). Tapping a
finding opens that bot's chat scrolled to that message with the match highlighted. Bot-name matches
stay at the top as "Bots".

**Design:**
- Query shorter than 2 characters does nothing beyond the current name filter; 250 ms debounce.
- Cap at a sensible page size (e.g. 50 findings) with "load more", never an unbounded dump.
- Case- and diacritic-insensitive; match inside long messages, snippet ±80 characters.
- Scope covers messages in that bot's stored session — the same transcript the app renders.
- Host-side: a bridge search endpoint over stored sessions (the bridge already knows each bot's
  stored session pointer), loopback/device-authenticated like the other `/v1/bots/**` routes. No
  transcript text in the response beyond the snippet.

**Decisions taken:** the empty state must say what was searched ("no messages on this host match
…"), not "no bot matches".

**Acceptance:**
1. A phrase that appears only inside a message — not in any bot name — returns a finding under the
   right bot.
2. Tapping the finding opens that chat at that message, highlighted.
3. Both apps return the same findings for the same query.
4. A 2000-message bot answers a search in under a second on the phone.

## R4 — Log viewer: refresh + order

**Platforms:** [shared] `ClientLogView` (reached from iOS Settings and the Mac About tab)

**Today:** a monospaced list, oldest first, no refresh (opening it is the only way to re-read) and no
order control.

**Requested:** two controls in the sheet's header row: **Refresh** (re-reads entries in place, keeps
the scroll position at the newest entry per the current order) and an **order toggle** with two
choices — "Newest first" and "Newest last" — defaulting to the current behaviour (oldest first, i.e.
"Newest last"). The chosen order is remembered per device.

**Acceptance:**
1. Refresh picks up an entry written after the sheet was opened, without re-opening the sheet.
2. The toggle reverses the list and keeps the position on the newest entry.
3. Order choice survives relaunch.
4. Copy-all and clear still work in both orders.

## R5 — Bot-to-bot messages rendered as people, not as prefixed text

**Platforms:** [iOS] [macOS] [bridge]

**Today:** `bot_message.py` labels the exchange in plain text inside the recipient's transcript
(`Assistant → Ops: …`) because the target's transcript renders every user row as if the owner typed
it. It is honest but it reads like data.

**Requested:** a first-class row type on both sides:

- in the **sender's** chat: `Messaged  <Aria's face> Aria`
- in the **recipient's** chat: `Message from  <Cody's face> Cody`

Rendered with the real bot face and display name, in the app's own row treatment (not the owner's
bubble, not a system banner), with the message text directly beneath the attribution line. If the
other bot has no face, the same deterministic default portrait the bot list uses. If the other
profile is not a bot this host knows, fall back to the profile id in monospace rather than a wrong
face.

**Design:** the bridge already knows `from`, `profile` and the session it delivered into — it emits
a structured row (`kind: bot_message`, `from_profile`, `to_profile`, `text`) instead of a text
prefix, and the apps resolve faces by profile id through the cache they already hold
(`app.botFaces`). Legacy rows that carry only the `Assistant → Ops:` prefix still render correctly —
they are matched and upgraded, not left broken.

**Decisions taken:** tapping the attribution opens that bot's chat (see open questions).

**Acceptance:**
1. A bot-to-bot message shows the correct face, name and wording on **both** sides.
2. No message text is duplicated (once as prefix, once as body).
3. Rows written before this change still read correctly.
4. Voice/read-aloud reads the attribution as words ("Aria messaged"), not the raw ids.

## R6 — Bot categories

**Platforms:** [iOS] [macOS] [bridge or local store — see open questions]

**Today:** one flat list, pinned bots first, hidden bots behind a switch. No grouping.

**Requested:**
- A new verb in the plus menu: **Add category** (alongside Add bot, Manage bots, New group chat).
- **Manage bots** gains a category control per bot: pick an existing category or create one inline.
- Bots with no category fall into a default group labelled **Uncategorized**, which always exists
  and cannot be deleted or renamed.
- The bot list renders one collapsible header per category: name, count, chevron. Collapsed state is
  remembered per category per device. Pinned bots stay above all categories, in their own group.
- Category order: alphabetical, with Uncategorized last; categories can be renamed and deleted.
  Deleting a category returns its bots to Uncategorized — never deletes them.
- A category with no bots still shows (with a 0 count) so it can be populated or deleted.

**Acceptance:**
1. Creating a category, assigning two bots, collapsing the group and relaunching preserves bots,
   assignment and collapse state.
2. Deleting a category moves its bots to Uncategorized; no bot disappears from the list.
3. Both apps show the same categories and the same membership.
4. Search results (R3) still show which category a finding's bot belongs to.

## R7 — Swipe actions on bot rows, icon only

**Platforms:** [iOS] — [macOS] parity per open questions

**Today:** pin and mark-read live in the row's context menu (long press / right-click) and in the
per-bot settings sheet. `model.isPinned` and the unread counters already exist.

**Requested:**
- **Swipe left** (trailing edge) reveals **Pin** / **Unpin** (same glyph pair the context menu uses:
  `pin` / `pin.slash`).
- **Swipe right** (leading edge) reveals **Mark as unread**.
- **Icons only** — no text labels in either reveal, per the request. The accessibility label still
  carries the words.
- Full-swipe (past the threshold) performs the action; haptic on commit; the row animates back.
- Swiping never opens the chat; the row's tap target is unchanged.

**Decisions taken:** the directions are as dictated (left = pin, right = unread) even though Mail
puts pin on the trailing edge too — that matches. Colour: pin uses the accent tone, unread uses the
muted/success tone already in `Tokens`.

**Acceptance:**
1. Both directions reveal one icon each, no text.
2. Pin/unpin and mark-unread update immediately, on both apps where implemented.
3. VoiceOver reads "Pin Aria" / "Mark Aria as unread".
4. A fast horizontal flick does not open the conversation (the drawer's drift guard rule applies
   here too).

## R8 — One window/sheet language across both apps

**Platforms:** [iOS] [macOS] [shared]

**Today:** sheets, panels and settings windows have grown independently — different corner radii,
header heights, backgrounds, dismissal affordances, and title treatments. The Mac mixes `.sheet`
windows with its own inspector-style panels.

**Requested:** a written audit of **every** modal surface in both apps, then alignment to one spec:

- corner radius, backing material/opacity, and border for sheets on each platform;
- a single header treatment (title type, subtitle presence, close/done placement and glyph);
- consistent padding, divider colour, and control heights inside them;
- consistent presentation animation and dismissal affordance (swipe-down on iOS where it applies,
  escape on the Mac);
- Mac: sheets that are really pages become windows/panels of a consistent size, and vice versa.

**Deliverables:** a table in `docs/UI-WINDOWS.md` listing every surface, its current values, and the
shared token it now uses; the tokens live in `Tokens`/`TypeScale`/`Geometry` so a future surface
cannot drift.

**Acceptance:**
1. The audit table covers every sheet, panel, alert and settings window in both apps — no "misc".
2. Side-by-side screenshots of before/after for at least five surfaces per app.
3. No surface uses a literal radius/padding that duplicates a token.

## R9 — Long-conversation performance, round two

**Platforms:** [iOS] [macOS] [shared]

**Today:** the last pass helped; a bot with a long transcript still goes sticky — input latency,
scroll hitches, and a stalled feel while streaming.

**Requested:** profile the long-chat path and fix what the numbers point at, with measurements:

- measured baseline first: a 2000+ message bot, frame times while streaming, time-to-first-row after
  opening the chat, scroll hitch count;
- the expected culprits, to be confirmed rather than assumed: whole-transcript re-diff per token,
  markdown re-parsed on every body pass, no windowing of off-screen rows, autoscroll arithmetic on
  every layout, and preview/metadata work happening on the main actor;
- fixes must keep behaviour identical: scroll-to-bottom, search highlight, jump-to-message, block
  rendering, attachments.

**Acceptance:**
1. Before/after numbers for the three metrics above, in the release notes.
2. Typing into a 2000-message bot while it streams stays responsive on an iPhone 16 Pro.
3. Opening that bot's chat is visibly faster (time-to-first-row), and scrolling is smooth.
4. No functional regression in search, jump-to-message or block interaction.

## R10 — Editable default soul for new bots

**Platforms:** [iOS] [macOS] [bridge]

**Today:** a new bot with no soul gets Hermes's own default — the "a Hermes agent from Nous
Research…" identity — and the only way to change it is per bot, after creation.

**Requested:** a settings field (Settings → Bots, or wherever soul-related settings already live)
holding the **default soul instructions** used for bots created from this app. Editing it replaces
that stock line for every future bot. Empty means "use the Hermes default" and says so. Existing
bots are untouched — the field applies at creation only.

**Design notes:** the default lives in the host's profile creation path, not in this repo (there is
no such string in `Bridge/`, `Sources/` or `Apps/`), so this needs a bridge-side setting with a
`GET`/`PUT` pair and a creation call that sends the soul explicitly. Multi-line editor with the same
treatment as the existing soul editor sheet, plus "Restore Hermes default".

**Acceptance:**
1. Setting a custom default and creating a bot yields a bot whose soul is the custom text.
2. Clearing it creates bots with the stock Hermes default.
3. No existing bot's soul changes.
4. The value is shared by both apps (host-side), and the field shows what will actually be applied.

## R11 — Bot-list size slider

**Platforms:** [iOS] [macOS]

**Today:** one fixed row size (`Geometry.rosterAvatar` and the adjacent type sizes).

**Requested:** Settings → Appearance gets a **Bot list size** slider:

- default position = exactly today's look (so nothing changes until it is dragged);
- dragging left shrinks the whole row — face, name, subtitle, badge, row height and spacing;
- dragging right grows all of them;
- a live preview row sits directly under the slider so the effect is visible before leaving settings;
- applies to the bot list in both apps; the conversation header is a separate surface and does not
  follow this slider.

**Design constraints:** scale as a ratio over the existing tokens (clamped, e.g. 0.85–1.35 of
current), never a per-element fudge; respect Dynamic Type (the slider scales the base, Dynamic Type
still adds on top); the slider value persists per device.

**Acceptance:**
1. Default position reproduces today's screenshot pixel-for-pixel.
2. Both extremes look intentional — nothing clipped, badges still inside the face, subtitle still one
   line with an ellipsis.
3. The change applies without relaunch and survives it.
4. Sizes computed through the token layer, not literals.

## R12 — Custom backup of bot data as JSON

**Platforms:** [iOS] [macOS] [bridge]

**Today:** memory, soul, description, routines, icon and model are readable per bot through the
existing endpoints; there is no export.

**Requested:** Settings → **Export bot data** writes a JSON backup of **every bot on the host**,
including:

- identity: profile id, display name, description, category, pinned/hidden state;
- soul and memory documents in full;
- routines (schedule, prompt, model, enabled state) in full;
- the model/provider choice, and the icon reference.

**Design:**
- one file per export, versioned (`"schema": 1`), with an exported-at timestamp and the host it came
  from;
- delivered through the iOS share sheet / Files and the Mac save panel; default name
  `hermey-bots-<host>-<date>.json`;
- the bridge gains one bulk export route so the app does not make N×5 requests, and the same route
  is what a future import would read;
- no credentials, tokens or device keys in the file — ever (assert this in a test).

**Acceptance:**
1. An export of a host with several bots contains every bot, with soul and memory non-empty where
   the bot has them.
2. The file is valid JSON matching the documented schema, and re-reading it reconstructs each bot's
   fields losslessly.
3. No secret material appears anywhere in the file (grep the fixture in a test).
4. The export includes bots that are hidden, paused or uncategorized.

## R13 — Codebase audit: security + bugs

**Platforms:** whole repo (Swift apps, shared sources, Python bridge, tools, CI)

**Requested:** a full pass, written up and fixed:

- **Security:** bridge authentication and the loopback-only exception path, device token issue/rotate/
  revoke, path handling in attachments/assets/icons (traversal, symlinks, content-type sniffing),
  anything that resolves a profile id into a filesystem path, the pairing claim wire, prompt/injection
  surfaces where a bot's text reaches another bot or the shell, and secret handling in the app
  (Keychain classes, nothing in defaults or logs).
- **Bugs:** Swift concurrency (actor isolation, `@MainActor` hops, task leaks on view teardown),
  force-unwraps and array index assumptions, JSON decode paths that silently swallow errors, retry
  loops without backoff, and dead/duplicated code that will rot.
- **Hygiene:** no secrets committed, dependencies and CI actions pinned, tests green, and a check
  that the release path still verifies what it claims.

**Deliverables:** `docs/AUDIT-2026-11.md` with findings by severity (critical/high/medium/low), the
file and line, the fix applied, and a regression test where one was possible. Unfixed items stay
listed with a reason — never silently dropped.

**Acceptance:**
1. Every finding is either fixed with a test or explicitly deferred with a reason.
2. `swift build`/typecheck and the bridge's test suite pass.
3. No credential, token or private key in the tree (`gitleaks`-style scan in the report).
4. A one-page summary of what changed and what a reader should re-check.

## Open questions (do not block wave 1)

1. **Categories:** stored on the host (shared across every device) or per device? Recommendation:
   host — two devices showing different groupings would be a bug report on day one.
2. **Backup scope:** conversations too, or bot configuration only? And is import expected in this
   batch or a later one? (Current spec: configuration only, no import yet.)
3. **Bot-to-bot rows:** should tapping the attribution line open that bot's chat, or is it
   information only?
4. **Search scope:** transcript text only, or also memory/soul/notes/routines, and does it include
   group-chat rooms?
5. **Swipe actions on the Mac:** trackpad two-finger swipe on rows, or the same verbs in the row's
   context menu and on hover? Two-finger swipe conflicts with horizontal scroll in the sidebar.
6. **⌘E on iPad with a hardware keyboard:** wire it up too, or Mac only for now?
