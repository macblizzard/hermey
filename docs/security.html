Docs / Security

Security model and threat model

The client puts a phone on a host that can run shell commands, read a vault and edit files. The whole security design is one sentence: the tailnet is the wall, the device is the identity, and the client can only answer questions the agent asks — never give itself permission.

This document states the trust boundaries, the invariants that hold them up, the threats those invariants are for, and the evidence (a test, or an explicit gap) for each one.

The Python bridge this document was first written about has been removed. Its code lived in Bridge/hermes_bridge, which is no longer in this repository. The host service now is hermeyd/ (Rust); its contract, its routes and its own tests are HERMEYD.md. §1's boundaries and §3's threats are the ones that hold today. §2's table is kept as the bridge's own audit — the reasoning behind the controls, with module and test names that are historical — and says so at its head.

Scope: hermeyd, the service that runs on the host today, the wss:// path into it, and the approval semantics the client relies on. The Swift apps' own storage (a this-device-only Keychain item, or a 0600 file on the unsigned Mac build) is described where it matters, but not audited here.

1. Trust boundaries

┌── iPhone / Mac ─────────────┐        ┌── hermes (100.64.0.1) ─────────────────────────────┐
│ Ed25519 key in Keychain     │        │  tailscale serve (serve-root) ──TLS 1.3──► 8788     │
│ refresh token in Keychain   │        │                                        │            │
│  ── 30 s WS ticket ─────────┼── wss ─┼─► hermeyd (Rust, loopback only)                     │
│                             │        │        │ allow-list, frame cap, audit              │
└─────────────────────────────┘        │        ▼                                            │
                                       │  127.0.0.1:9121/api/ws  (Hermes engine)             │
                                       │  agent runtime · tools · approvals · vault          │
                                       └─────────────────────────────────────────────────────┘

The Mac build ships unsigned and has no keychain entitlement, so it keeps those same items in a 0600 file under ~/Library/Application Support/Hermey/, excluded from backups; the phone uses the Keychain alone.

Boundary Crossing it requires What is on the other side
Public internet → tailnet Tailscale identity + ACL nothing (no public ingress exists)
Tailnet → hermeyd TLS to tailscale serve, then a single-use 30 s ticket pairing, tokens, /v1/ws
hermeyd → gateway loopback + the gateway token (never sent to a device) full authority over the agent
Gateway → app a server→client JSON-RPC request (approval, clarify, sudo, secret…) a human decision
App → gateway the client method allow-list sessions, prompts, discovery

Three consequences worth stating plainly:

  • A compromised device is a compromised user, not a compromised host. The allow-list has no shell.exec, cli.exec, config.set or vault.*; the worst a stolen phone can do is drive sessions the user could drive anyway, and answer approvals — which is why approvals are rendered, not auto-accepted.
  • A compromised host service is already root on the box. Loopback-only, token-gated and audited, but it adds no privilege; the point is that it does not widen what an attacker on the host can do.
  • The tailnet is the outer wall. Every control below assumes an attacker who is already on the tailnet or has stolen a device; controls that assume "nobody can reach the port" are marked as such.

2. Invariants, and where each one is enforced today

The table below is the audit of the retired Python bridge. It is kept because it is the reasoning behind the controls and records what each row used to be pinned by — not as a description of hermeyd. The modules and test_* names in its last two columns went with Bridge/hermes_bridge; there is no Tools/qa to run any more.

For the service that runs today the evidence is its own code and tests:

cd hermeyd && cargo test                 # the unit and route tests, in hermeyd/src
scripts/smoke-hermeyd.sh                 # end-to-end: real HTTP, real state, prints PASS per check

scripts/smoke-hermeyd.sh is the one that proves the properties a reader cares about most — health, a minted single-use code, a registered device, a rejection on replay, a bearer-less 401, a refused revoke, and a refused non-loopback bind. Where a row below states a number, check it against hermeyd/src before quoting it: pairing codes are 6 digits (not 8), the code TTL and device cap are the constants in hermeyd/src/routes.rs (PAIRING_CODE_TTL_SECONDS, MAX_DEVICES), and the attempt throttle lives in hermeyd/src/pairing.rs.

3. Threat model

Format: threat → what the attacker wants → control → residual risk. The tests named above are the evidence; this table is the reasoning.

# Threat Goal Control Residual risk
T1 A device on the tailnet that was never paired drive the agent /v1/ws requires a ticket from /v1/token, which requires a refresh token from a pairing claim; a claim requires a code only the host can mint (invariant 2, 10–12) a tailnet member can still reach /v1/health, /v1/pair/claim and /v1/push/icon/<profile>.png (see T2 and the surface map)
T2 Brute force of the 6-digit pairing code pair an unauthorised device 600 s TTL, single use, 30 attempts/minute/source (invariant 3–4). One source gets 30 guesses per 60 s window against 10⁶ codes — 300 guesses over a code's life, a 1-in-3 300 chance throttling is per source address; 1 000 tailnet addresses get ~300 000 guesses per window, roughly a one-in-four chance per code, and a missed code is dead
T3 Stolen bridge.db (backup, misconfigured permissions, root on host) mint tokens refresh tokens are SHA-256 only (invariant 7); no gateway token in the DB root on the host is game over regardless (A1)
T4 Stolen refresh token (malware on the phone, backup extraction) impersonate the device the token is useless without the device_id, which is not secret — so a stolen token is enough (invariant 8 is integrity, not proof-of-possession) see G1: no signed assertion. Mitigation today is revocation + 15 min access tokens
T5 Replay of a captured WS URL hijack a session 30 s TTL, single use, consumed before accept (invariant 10–11); TLS prevents capture in transit a ticket captured from the phone's memory within 30 s is usable once — that requires code execution on the device
T6 Compromised client asks the bridge for more than the UI shows shell access allow-list (shell.exec, cli.exec, config.set, vault.* absent) and no generic proxy (invariant 13–14) a compromised client can still prompt.submit — i.e. ask the agent to run something, which then needs an approval the user sees (T8)
T7 Malicious/compromised gateway asks the app for something it cannot render stall the agent, or phish the user the bridge answers anything outside the six approved methods with -32601 (invariant 15) none material: fail-fast is the desired behaviour
T8 Approval fatigue / social engineering (the real risk) get a destructive action approved approvals are shown with tool + input + reason; declines_not_shown stays true; nothing auto-approves; the client cannot widen permissions (invariant 16–17) the human is the control. Show the command, not just the tool name
T9 Oversize frame / memory exhaustion DoS the bridge or the agent 16 MiB per frame both directions, close 1009, never forwarded (invariant 20) many small frames are still work; no per-request rate limit and no bandwidth quota (G4)
T10 Prompt text or tool output leaks into logs / journald / a bug report read the user's data AuditLog.emit has no parameter for payload and validates every free-form field against a token pattern; verified with a canary through a real turn (invariant 22) uvicorn access logs are off (access_log=False) but an operator can enable debug logging on the gateway
T11 Gateway token exfiltration full agent authority token never leaves the process except in the loopback dial URI; never in responses or audit (invariant 21) a host-level reader (/proc/…/environ) can still see it — root on host
T12 Revoked (lost/stolen) device keeps acting persist access refresh + tickets are refused immediately (invariant 9, 12) the live socket stays open until it reconnects — G2
T13 Client forges another device's server-request id to answer its approval approve something the user never saw ids are per-socket and remapped on collision; a stale answer is dropped (invariant 18–19) within one socket the app is the user; there is no second authenticator by design
T14 Relay is used as a general-purpose proxy into the host lateral movement allow-list both directions, no arbitrary URL/method pass-through, no file or shell surface the agent itself is the powerful surface — that is the product
T15 Protocol smuggling (weird method names, \n injection, binary frames) bypass the allow-list method names are regex-validated; frames are split and re-serialised per frame; binary frames are parsed as bytes and still capped; invalid JSON gets -32700 and is not forwarded a frame split across two WS messages is rejected rather than reassembled — safe failure (G3)

Accepted risks (by design, not bugs):

  • A1 Anyone who is root on the host owns the agent; the bridge adds no privilege.
  • A2 A paired device can read that profile's sessions. There is no per-session ACL; the user model is "my devices, my agent".
  • A3 Pairing is a shared secret shown on the host. Shoulder-surfing a QR code within its 600 s lifetime is a physical-security problem.
  • A4 The tailnet ACL is not enforced by this code. If a device is on the tailnet and not blocked by ACLs, it can reach /v1/health and attempt claims (T2 covers the cost).

4. Gaps

Each is a real difference between the design and the implementation, with the impact and the fix. The test_* names below are the bridge's own suite and are historical; the gaps themselves are statements about the bridge's design, so re-check one against hermeyd/src before relying on it.

G1 — no proof-of-possession on the token exchange (medium). POST /v1/token accepts {device_id, refresh_token}; the Ed25519 key registered at pairing is stored but never used to verify a signed assertion (02-architecture.md §6.4 asks for one). A stolen refresh token is therefore a bearer credential. Fix: sign {device_id, timestamp, nonce} with the device key, verify with the stored public key, reject clock skew > 60 s, and rate-limit per device. Until then, keep the refresh token in the Keychain with kSecAttrAccessibleWhenUnlockedThisDeviceOnly and rely on revocation. The unsigned Mac build cannot use the Keychain, so there it lives in the 0600 file described above.

G2 — revoking a device does not drop its live socket (fixed). The runtime keeps a device_id → set[socket] map (proxy.LiveSessions), and DELETE /v1/devices/{id} closes every live relay for that device with 4401 before answering (sockets_closed in the response). The socket that was already upgraded is therefore torn down from this side, not on the client's next reconnect. Invariant 9 covers both the new token and the open socket now.

G3 — a frame split across WebSocket messages is rejected, not reassembled (low). test_a_chunked_frame_is_rejected_rather_than_half_forwarded pins the behaviour: each half gets -32700, nothing is forwarded. The Swift client sends one frame per message (JSONRPCCodec.encodeFrame), and the gateway's WS transport does the same, so this is not a live path. Fix if it ever matters: accumulate a partial buffer with the same 16 MiB ceiling.

G4 — no per-request rate limit (low). The socket caps are in place in hermeyd/src/relay.rs: a device may hold four sockets and a host 64, and at the cap the longest-idle socket is evicted with 4429 rather than the newcomer refused (a device's last socket is never taken). What is still missing is a limit on the requests one socket may send and on bandwidth, so a paired device can still generate load up to whatever the engine answers.

(Four sockets per device is the figure the Python bridge's proxy.py used; hermeyd implements it.)

G5 — gateway close codes are collapsed into 1011 (low, UX). When the gateway closes with one of Hermes' own codes (4009 session busy, 4004, 4018 …), the app sees 1011 "gateway closed" and cannot tell a busy session from a gateway restart. test_gateway_close_reaches_the_client accepts either code today. Fix: forward the upstream close code when it is in the app's known set, else 1011. (The 4403 used by that scenario is illustrative; the recorded fixtures contain no close frames.)

G6 — approval payload shapes are unverified (informational). No approval frame exists in fixtures/, so params.choices/call_id in the scenarios are modelled from the architecture doc. The envelope and blocking semantics are tested; the field names are not. Fix: record one real approval from the live gateway into fixtures/approval.ndjson and diff.

G7 — pairing-code throttle is per source address (informational). See T2. Sufficient while the tailnet is small and ACL'd; a global counter plus a per-device backoff would be stronger.

5. Operating it

Start (systemd; the unit is written by setup/install.sh):

sudo systemctl start hermeyd
tailscale serve --bg http://127.0.0.1:8788        # serve-root, no port

hermeyd refuses any bind but loopback, and refuses a published port equal to the browser channel's.

Rotate the engine token: stop hermeyd, rotate the token on the engine side, update HERMEYD_ENGINE_TOKEN_FILE in /etc/hermey/hermeyd.env, start. Live sockets drop and the app reconnects with a fresh ticket. No device has to re-pair.

Revoke a device: DELETE /v1/devices/{id} (or the app's device list). Kills the refresh token, any unused ticket, and every live socket of that device (4401) — the relay map is closed from this side rather than waiting for the phone to reconnect.

Read the audit log: one JSON object per line, written beside bridge.db in the state directory. Fields: ts, event, device, method, bytes, duration_ms, direction, outcome, reason, close_code. Event names are a closed set (hermeyd/src/audit.rs), so a typo fails a test instead of shipping silently. Look for ticket_rejected, client_request_rejected, server_request_declined and frame_too_large — those are the four signals that something is probing the host.

Incident: a device is compromised. Revoke it, rotate the engine token (closes every live socket), check the audit for client_request from that device around the compromise window, and review which approvals were answered (server_response) in that window — the host records that an approval was answered, never what the prompt said.

6. What is deliberately absent

No accounts, no telemetry, no cloud relay, no public ingress, no second copy of your data, no "danger-full-access" default, no auto-approve, no per-device passwords, and no way for the client to escalate its own permissions. hermeyd is a single Rust binary small enough to read in an afternoon, which is the point.

Surface map: what is reachable without a device ticket

Every /v1/** route consumes a single-use 30 s ticket in Authorization: Bearer …, except the handful below. They are unauthenticated on purpose and bounded on purpose; anything added here needs the same reasoning written next to it.

Route Why it is open What it is bounded by
GET /v1/health liveness for the installer and hermeyd --gateway-check returns {status, protocol_version, ws} only — no device count, no version of anything else
POST /v1/pair/start the host mints the code direct loopback only: any Forwarded / X-Forwarded-For / X-Real-IP / Tailscale-User-Login header means it arrived through tailscale serve and is refused 403
POST /v1/pair/claim the phone redeems the code it was shown a live 6-digit code (single use, 600 s), 30 attempts/min/source
POST /v1/token trades a refresh token for a ticket a SHA-256 match against device_id + token; refused for a revoked device
GET /v1/push/icon/{profile}.png Bark fetches the image itself and holds no credential only a bot's face and whether that bot exists; the profile name is ^[a-z0-9][a-z0-9_-]{0,63}$
WS /v1/display/ws noVNC cannot set a header on its socket accepts, then redeems a single-use 60 s display ticket and re-checks the device; a bad ticket closes 4401

POST /v1/bots/{profile}/message is different again: it takes no ticket, because it is an operator command for the agent on the host, and it is refused 404 for any caller that arrived through a proxy (same loopback rule as pair/start).

Known residual risks (2026-11 audit)

Written down because each is a real gap that is not hidden by the allow-list:

  • The Bark relay endpoint is device-supplied. POST /v1/push/register takes a URL a paired device types, and the watcher POSTs banner JSON to it. A paired device can therefore make this process issue an HTTP POST to any host it can reach (loopback included) — a stored SSRF. Redirects are now refused (push._NoRedirect), so the destination is exactly what was registered, but the registration itself is not restricted to public addresses because a self-hosted Bark server on the LAN is the normal deployment. A paired device is already root-equivalent (above), so this adds no reach; it is listed so nobody mistakes the relay for a hardened egress path.
  • access_token in POST /v1/token is inert. The response carries a random access_token that no route accepts; only ws_ticket is a credential, and it is single use. A client that stores access_token and sends it gets 401. Kept for wire compatibility with shipped app builds.
  • A pairing code is a shared secret on the host's screen (A3). Its window is 600 s and clamped to 30–3600 s by app._pairing_ttl, so a mistyped override cannot mint a year-long code.
  • Two processes on the same state are not coordinated. The store takes an in-process lock and publishes with an atomic rename, which covers the one service a host runs. A second hermeyd pointed at the same state directory (/var/lib/hermeyd) is unsupported.

Bot-to-bot messages

POST /v1/bots/{profile}/message lets the agent on the host speak into another bot's chat, in the session the apps open. It is loopback only (off-host it answers 404, like any unknown route), it mints no ticket and writes no device row, and it refuses a profile with no stored conversation rather than creating one nobody can find. The audit log records the pair and whether a reply came back — never the words, which are the owner's conversation. A paired device does not need this route: it types into the chat itself, and letting a phone impersonate another bot would hand it a privilege it has no use for.

Threat model, stated plainly (2026-11 audit)

Three things this bridge does not defend against, written down because a reader of the allow-list could otherwise conclude the opposite:

  • A paired device is a root-equivalent credential. The method allow-list stops a client calling shell.exec directly, but prompt.submit is allowed, and the agent's own tool loop can run commands — including approvals, which the bridge relays to the socket that submitted the prompt. Treat a device ticket like an SSH key to the host, not like a scoped API key. The smallest real fix is a host-side confirmation for approval/sudo; until then, revoke a device you no longer control immediately.
  • The Ed25519 key is recorded, not verified. Pairing stores the device's public key, and /v1/token exchanges the refresh token without a challenge, so the key proves nothing today: a stolen refresh token is usable from any host. Either implement nonce + signature on /v1/token, or treat the refresh token as the whole credential (which is what the code does).
  • Device revocation is a shared secret's power. Any paired device can revoke any other. That adds no reach a ticket does not already have (see the first point) — it is listed so nobody mistakes the device list for an authorisation boundary.

Bot management (paired device)

A paired device can now create, disable and delete bots, and rewrite any bot's SOUL.md. This is a deliberate widening of the device's reach, and it is small in practice because a paired device is already root-equivalent (a device ticket buys shell access, see the threat model above). What the new verbs add is authority over other bots, not reach outside the host.

  • SOUL.md is written through profiles.configure (soul section only) and capped at 64,000 characters in the allow-list: a SOUL.md is injected into every turn of that bot, so an accidental megabyte paste would be paid for on every message it ever answers.
  • Disable marks the bot disabled in the service's own documents store (bots_disabled in /var/lib/hermeyd/bridge.db), and a disabled bot refuses POST /v1/bots/{profile}/message: otherwise another bot could make a disabled bot answer. It does not yet stop that bot's scheduled jobs — that is the next piece of the routines work, and until it lands a disabled bot's routines still fire.
  • Delete archives the profile to /var/lib/hermeyd/deleted-bots first, then removes the directory itself and refuses to report success if the directory is still there. The archive is a mistake-catcher, not a backup contract.
  • hermeyd runs under ProtectSystem=strict with /var/lib/hermeyd as its only ReadWritePaths entry and ProtectHome=no, because the engine home is often under the service account's home (deploy/hermeyd.service). A write into a profile — a restored SOUL.md, a bot's skill — lands in the engine's profiles as that same UID, which is why the two must share one.

Bot computer (shared desktop)

One headless desktop serves every bot on the host, on purpose: one Xvnc, one Chromium user-data-dir, one control lease. The consequences, stated rather than implied:

  • Logins are shared. A site signed into during a takeover is signed in for every bot on that host, and in every later session until the site expires it. That is the feature; it also means a bot can act on any site you signed in to.
  • The lease is a tool-level fence, not an OS one. While a human holds it, computer_use and the browser tools are refused (human_has_control), but a process the agent starts by hand against the published DISPLAY is inside the documented same-user boundary.
  • The viewer path. /v1/display/* is device-authenticated with the same single-use ticket as every other route; observe mints a bridge ticket (60 s, single use, bound to device + profile) and holds the gateway's own ticket inside the process. The socket carries its ticket in the query string because noVNC cannot set a header — the same trade-off the dashboard makes, with the same one-minute lifetime. Revoking a device closes an open viewer.
  • Audit records display_open / display_close with device, profile, close code and byte count — never frame content, because a screen shows passwords.
