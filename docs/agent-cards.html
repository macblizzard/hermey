Native agent cards in Hermey

A bot draws an approval, a task or an email draft as a card instead of a paragraph.

Status: draft spec · owner: Aria · target: Hermey 0.1.616+

Why

The agent-cards skill gives a bot three things it currently cannot ask for properly: an approval before anything outward or irreversible, a task card for a job that runs for minutes, and a draft email the owner edits and sends. It emits a small JSON file plus one marker line in the reply.

Today only Grokbot Override draws those cards, and that is a Hermes Desktop plugin: a JS bundle the Electron (or browser-hosted) client loads. Hermey has no plugin host — 126 Swift files, no desktop-plugins reference — so for us the marker degrades to plain text.

Cards are the right shape for the one thing Hermey is still weak at: letting the owner approve an action with the payload in front of them. This spec renders card.v1 natively, so any bot that uses the skill works on iPhone and Mac without Electron.

The contract we must honour

The skill's wire form is one line, on its own, outside code fences:

::card{id="c-9b" kind="approval" file="cards/c-9b.json"}

file is relative to the session's working directory; id and kind must match the file. One line per card, never two for the same card.

The file (cards/<id>.json, ≤ 32 KB):

Field Rule
schema required, exactly "card.v1"
kind required: approval | task | draft-email
title required, non-empty
status.state required: pending | running | done | error | awaiting-approval
status.label optional chip text override
body[] optional: {type:"text", text} | {type:"kv", rows:[[label,value]]} | {type:"fields", items:[{label,value}]}
email for draft-email: {to, cc, subject, bodyText}
actions[] ≤ 3: {label, send, style?: "primary"|"danger"}
resolved null, or {action, at} once the owner chose

Live behaviour the skill promises: while the chat is open, a card in one of the last eight messages re-reads its file every 3 s for up to 30 min, and stops when the file is final (resolved set, or status.state is done/error). To update a card, the bot rewrites the same file.

Transport: how Hermey gets the JSON

The file lives on the host in the bot's working directory; the client only has the transcript. So the engine resolves it, not the client:

GET /v1/cards/{id}?session=<session id>&message=<message id>   (hermeyd proxies to the engine)
→ 200 {"card": {...}, "mtime": "...", "final": false}
→ 404 {"error": "no_such_card"}              → the client draws "Card not available"

Why server-side resolution:

  • Path safety — the client never sends a path, only an id. The engine resolves <session.cwd>/cards/<id>.json and refuses anything outside that directory (no .., no absolute paths, no symlink escape; id must match ^[A-Za-z0-9_-]{1,40}$).
  • Remote engines — Hermey talks to hermeyd over the tailnet; reading host files directly was never an option.
  • Live updates — a re-read is a re-fetch; nothing has to be pushed over the socket.

Rejected alternative: inlining the card JSON in the marker (as A2UI surfaces do). Simpler, but it cannot honour the 3-second task updates — those need re-reads.

The card must still draw a week later

The skill keeps its file in the chat's working directory, which can be cleaned up, rewritten by a later turn, or simply gone when the transcript is reopened. So the first successful read is snapshotted, and replay draws the snapshot:

  • On the first GET /v1/cards/{id}, the engine stores the resolved JSON against (session, message id, card id) — message-addressed, so two messages naming the same file never collide, and a later turn rewriting that file cannot retroactively change history.
  • Live polling moves the snapshot forward with each read, so the last state a reader saw is the state a later reader sees.
  • File gone, snapshot present → draw the snapshot with its last known status. "Card not available" is reserved for a marker whose file was already missing on first read.
  • Storage: one row per message+card in the profile database, capped at the card's own 32 KB.

Client design

New target HermesCards (Foundation + SwiftUI, depends on HermesKit only):

Piece Responsibility
CardMarker finds ::card{…} lines, returns refs (id, kind, file); strips the line from prose
CardModel lenient Decodable for card.v1; unknown fields ignored, a broken file yields .unavailable
CardStore fetch + poll per card: every 3 s while pending/running/awaiting-approval and resolved == nil, stop at 30 min or when final; cache by id
CardView the three layouts, status chip, body blocks, ≤ 3 buttons
Transcript hook same shape as the A2UI branch: if a card marker is present, draw prose then the card

Polling stops when the row scrolls out of the last eight messages, when the app backgrounds, and when the file is final. On foreground, one refetch.

Actions

Tapping a button sends action.send as a user turn (that is the value the skill designs for: APPROVE c-9b book the cabin). The card ticks the chosen label optimistically and settles on the next poll — the bot is expected to rewrite the file with resolved.

A live draft is the one exception, and only in what the send text is: Send posts one deterministic block built from the fields as typed — the card's own send token on the first line, then send this email exactly as written:, To:, Cc: (omitted when empty), Subject:, a --- rule, and the body. It goes out through the same path, so nothing downstream changed. Discard is local: it greys the card and posts nothing at all.

v1 shows that turn in the transcript. Hiding it (what Grokbot does) needs a per-message hidden flag; the engine currently exposes only session-level hidden (session.set_hidden). Tracked as an enhancement, not a blocker: the send strings are short by design.

Rendering

  • approval — title, body, buttons. No status chip.
  • task — status chip (running with spinner, done, error), body, optional Stop button in danger style.
  • draft-email — a form, not a poster: To/Cc/Subject are text fields and bodyText is a multi-line editor, always, with no "Edit" step. The card ends in exactly two buttons, Send and Discard, whatever actions[] the file wrote; an action labelled Edit is not drawn. A draft with no email block cannot be typed into and draws as before.
  • A resolved card is a receipt: no fields, no buttons, just the facts and the note.
  • A body that is one line under 200 characters and has no line breaks reads as the question under the title.
  • Styling comes from HermeyUI tokens, never from the card: primary maps to the accent fill, danger to the destructive tint. No model-chosen colours.
  • Text only. No HTML, no markdown injection, no remote images: a card is data.

Accessibility: the card is one element with children: .contain; each button is labelled by its label, not by send; the status chip reads its state in words.

Rollout and rollback

  • Flag cards.enabled in Hermey, default on since 0.1.621. Off → ::card lines render as text.
  • No change to genui (::blocks) or A2UI (::a2ui): three independent renderers, each preferred only when its own marker is present.
  • Server side is read-only: one new GET route. Nothing about the skill changes.

Phases

Phase Scope State
P1 CardMarker + CardModel + approval layout + fetch route + flag shipped — 0.1.621
P2 actions round-trip (send, optimistic tick, resolved receipt) shipped — 0.1.622
P3a task layout, body[] blocks, draft-email layout shipped — 0.1.622
P3b an editable draft: fields on arrival, Send and Discard only shipped — 0.1.623
P3c task live updates: re-read a card in the last eight messages every 3 s, stop when final not built
P4 a11y pass, snapshots, e2e with a live bot partly — fixtures and guards only

What is on the wire today: GET /v1/cards/{id}?session=&message=, snapshotted per message, one read per card per conversation visit. Polling is the remaining piece, and it is deliberately last — it is the only part that spends host time while nothing is happening.

Test plan

  • Fixtures: one valid file per kind, plus broken shapes (bad schema, missing title, 4 actions, 40 KB body, .. id) that must all degrade rather than throw.
  • Parser tests: marker found outside code fences, two markers in one reply, marker with an unknown kind.
  • Poll logic: fake clock — stops at final, stops at 30 min, refetches on foreground.
  • View snapshots: three kinds, light/dark, long title, empty body.
  • E2E: a bot writes cards/c-…json + the marker; the card appears, a tap sends the send text, the bot rewrites with resolved, the buttons lock.

Decisions (settled 2026-11-22)

  1. Action sends are visible. A tap sends action.send as a normal user turn (APPROVE c-9b book the cabin); no hidden-message flag. The strings are short by design, and a visible record of "I approved this" is the better audit trail.
  2. Working directory falls back per profile. The route resolves <session.cwd>/cards/… first; when a session has no cwd it falls back to the bot's own profile directory (profiles/<name>/) before giving up. One code path, no client involvement.
  3. Cards must survive. Snapshots per message (see "The card must still draw a week later"), so a thread reopened next week still draws its approval, task and email cards.

Still open (smaller):

  1. A snapshot only moves forward while a chat is live — a file rewritten later, with no live reader, does not update history. Accepted for now.
  2. Should a resolved card stay full-size forever, or collapse to one line ("Approved: book the cabin") after a day? Leaning to collapse for approvals only.
