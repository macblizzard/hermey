# Mobile bridge integration

All changes require a bridge deployment; nothing here asserts that a running service has been updated. Use TLS off loopback.

* Icon API: see `bot_icons_integration.md`. Mint a **fresh** `ws_ticket` using `/v1/token` for each HTTP call and pass `Authorization: Bearer <ws_ticket>`. `access_token` is not valid authentication.
* Model: over the authenticated WebSocket send JSON-RPC `profiles.configure` with exactly `name`, `model`, `provider` (nonempty strings), and optionally boolean `confirm_expensive_model`. Check the gateway result's `ok`, `applied` and optional `confirm_required`/`confirm_message`; a transport-level success does not imply application success. Other configuration sections are denied. Gateway errors are redacted.
* Description: `profiles.configure` with exactly `name` and `description` (a string; an empty string clears it). `model`/`provider` are not required for this call. The same `ok`/`applied` check applies. Every other section — `soul`, `ui_meta`, skills, toolsets, MCP — stays denied.
* Attachments: authenticated WebSocket JSON-RPC `file.attach` with `session_id`, `name`, `data_url` of the exact form `data:application/octet-stream;base64,<base64>`; or `image.attach_bytes` with `session_id`, `filename`, `content_base64` (plain base64). Each must contain 1–8388608 (8 MiB) decoded bytes and arrives as one WebSocket frame, so base64 expansion (4 bytes per 3) must still fit `HERMES_BRIDGE_FRAME_CAP`. Names must be UTF-8, 1–255 bytes, not `.`/`..`, and must contain no slash, backslash, NUL, CR or LF. No extra fields. For a successful file response include `result.ref_text` in the next prompt; images are queued. Absolute host paths are removed from results; if a file is configured outside the session workspace and its reference is absolute, the bridge returns an error rather than expose it. Attachment upstream errors are redacted. Path-based, staged upload, PDF, clipboard and image-detach variants are not exposed even when explicitly added to the bridge extra-method list.

## Voice: proposed only, NOT implemented

Candidate contract for future coordinated implementation: `POST /v1/voice/transcribe` JSON `{ "mime_type": "audio/mp4", "content_base64": "..." }`, limit 10 MiB decoded, returning `{ "transcript": "..." }`; `POST /v1/voice/synthesize` JSON `{ "text": "..." }`, limit 4000 Unicode characters, returning `{ "mime_type": "audio/mpeg", "content_base64": "..." }`. Each would consume a separate fresh bearer `ws_ticket`; size, media types, error schema, profile scoping and output codec need validation before shipping. These routes currently do not exist. Hermes has `tools.voice_mode.transcribe_recording` and `tools.tts_tool.text_to_speech_tool`, but this bridge's isolated Python environment cannot import the Hermes `tools` package; a real provider and deployment/runtime integration have not been established or exercised. No client should rely on this proposal as an existing API.
